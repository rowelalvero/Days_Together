# Migration Roadmap

**PROPOSED.** This is the incremental, phased execution plan for the architecture defined across this specification and the ADRs. It exists so the migration can be carried out safely on a **live app with real user data**, by a **solo developer**, without a big-bang rewrite.

Every phase is independently shippable: the app builds, analyzes clean, and passes its test suite at the end of each phase, not only at the end of the whole roadmap.

## How to read this document

Each phase specifies: **Scope**, **Why this order**, **Files/modules affected**, **Risk**, **Validation**, and **Exit criteria**. A final section maps every one of the 22 Definition-of-Done items to the phase(s) that deliver it and the mechanism that verifies it.

## The two facts that set the whole order

**Fact 1 — the 13-provider fan-out on `RelationshipProvider` is fake coupling.** Verified by grep: every domain provider that reads `RelationshipProvider` reads exactly four members —
```
4  relationship.userId       2  relationship.partnerId
4  relationship.coupleId     2  relationship.isSupabaseAvailable
```
"Everything depends on the 2,143-line god provider" is, in reality, a four-field dependency. Extracting those four fields into a small `CoupleSession` (Phase 1) decouples all 13 domain providers in a matter of days, and is therefore done **first** — before Riverpod, before go_router, before anything else.

**Fact 2 — the god provider's state splits cleanly along three Supabase tables.** `RelationshipProvider` touches exactly `couples` (7 sites), `users` (8 sites), `license_details` (1 site), plus 41 SharedPreferences keys. State-ownership extraction (Phase 5) follows this exact partition, per ADR-002/ADR-003's finding that the June 2026 delegation refactor failed because it moved *operations*, not *fields*.

**Standing constraint, every phase:** the 41 SharedPreferences keys are a live hydration contract for real users on real devices. No phase renames a key. `PrefsKeys` (Phase 0) exists specifically to make this constraint enforceable.

### Formal row-mapping documentation (extracted from `lib/repositories/relationship_repository.dart` and its three model files, read in full as part of producing this specification — not reconstructed from memory)

`RelationshipRepository` maps three tables via three methods, each delegating to a model's `fromMap`/`toMap`:

**`couples` → `RelationshipWorkspace`** (`fetchWorkspace`, `lib/models/relationship_workspace.dart:36-74`):
`id`, `partner_a_id`→`partnerAId`, `partner_b_id`→`partnerBId`, `partner_a_email`→`partnerAEmail`, `partner_b_email`→`partnerBEmail`, `status` (default `'waiting'`), `pairing_code`→`pairingCode`, `recovery_lookup_key`→`recoveryLookupKey`, `recovery_code_hash`→`recoveryCodeHash`, `is_premium`→`isPremium` (default `false`), `start_date`→`startDate` (ISO string → `DateTime?`), `start_time_hour`→`startTimeHour`, `start_time_minute`→`startTimeMinute`, `story_title`→`storyTitle`, `created_at`→`createdAt` (ISO string → `DateTime?`). Consistent with the `couples` table columns referenced throughout the prior backend audit's RPC analysis (`partner_a_id`/`partner_b_id`, `status`, `pairing_code`, recovery fields) — current and trustworthy as Phase 4's `CoupleRepository` seed.

**`license_details` → `RelationshipMetadata`** (`fetchMetadata`, `lib/models/relationship_metadata.dart:18-38`):
`couple_id`→`coupleId`, `certificate_number`→`certificateNumber`, `issue_date`→`issueDate` (ISO string → `DateTime?`), `anniversary` (ISO string → `DateTime?`), `theme`, `relationship_title`→`relationshipTitle`.

**⚠️ Investigated further and resolved — the finding is more significant than a stale model, and corrects an earlier draft of this specification. Full trail, verified against `supabase/migrations/` directly:**

`license_details`'s original `CREATE TABLE` (`20260621000000_remote_schema.sql:154-183`) has `couple_id`, `creator_id`, and **30 paired `your_*`/`partner_*` text/timestamp columns** — `your_name`/`partner_name`, `your_gender`/`partner_gender`, `your_phone`/`partner_phone`, `your_birthdate`/`partner_birthdate`, `your_address`/`partner_address`, `your_nationality`/`partner_nationality`, `your_weight`/`partner_weight`, `your_height`/`partner_height`, `your_blood_type`/`partner_blood_type`, `your_eye_color`/`partner_eye_color`, `your_conditions`/`partner_conditions`, `your_date_issued`/`partner_date_issued`, `your_signature`/`partner_signature`, `your_avatar_path`/`partner_avatar_path`. These names match the app's 28 license fields almost exactly.

**But the live Dart code does not read or write those 28 fields through `license_details`.** `relationship_provider.dart`'s `updateLicense()` method pushes them through `ProfileService.updateUserDetails()`/`ProfileService.updatePartnerProfile()` (the latter via the `update_partner_profile` RPC) — both targeting the **`users`** table, whose own columns (confirmed via `UserProfile.fromMap`, `lib/models/user_profile.dart:44-66`, and the `update_partner_profile` RPC's column whitelist from the prior security audit) independently carry the *same conceptual fields* as singular, per-person columns (`gender`, `phone`, `birthdate`, `address`, `nationality`, `weight`, `height`, `blood_type`, `eye_color`, `conditions`, `date_issued`, `signature`, `avatar_url` — one row per user, not one row per couple).

**This means the live schema has genuine field duplication across two tables**, and `license_details`'s 30 paired columns appear to be a holdover from an earlier design (per-couple storage) superseded by the current per-user `users`-table design, without ever being dropped. Meanwhile, `certificate_number` — inserted by `create_relationship_workspace` (`20260712000001_refactor_users_profiles.sql:165-166`: `INSERT INTO public.license_details (couple_id, certificate_number) VALUES (...)`) — **is never created by any tracked migration.** No `ALTER TABLE ... ADD COLUMN certificate_number` exists anywhere in `supabase/migrations/`. The dead repository's `RelationshipMetadata` model, which includes `certificateNumber`, therefore reflects real, live-inserted data that simply isn't visible from the migrations directory alone — confirming **the migrations directory does not fully capture the live `license_details` schema** (undocumented drift, likely from dashboard-applied changes never captured in a migration file).

**Correction this requires to the rest of this specification:** `LicenseController` (Phase 5's second extraction) owns the 28 license fields' **application state**, but its repository dependency is `UserRepository`, not `LicenseRepository` — the live write path is `users`, confirmed above. `LicenseRepository`/`license_details` remains one of the three repositories under ADR-003's test (it is read by `ProfileService.fetchLicenseDetails` and subscribed to via realtime at `relationship_provider.dart:576`), but its actual scope is the narrower **certificate/metadata** concern (`certificate_number`, and whatever the undocumented-drift columns turn out to be) — not the 28 paired fields. `state-management.md`'s Riverpod topology diagram and `architecture-overview.md`'s Diagram 6 are corrected to show `LicenseController → UserRepository` accordingly.

**Mandatory Phase 4 action, elevated from "re-verify" to "required":** before building `LicenseRepository`, connect to the live Supabase project and run `\d license_details` (or the Supabase dashboard's schema view) to get the actual current column list — do not trust the migrations directory alone for this one table, since it is now confirmed incomplete. Determine at that point whether the 30 legacy `your_*`/`partner_*` columns are still populated by anything, are read by any surviving UI, or are safe to formally deprecate (a separate, future decision — not made by this planning phase, and not a schema change this migration performs).

Also present in the dead repository, not row-mapping but RPC pass-throughs worth preserving as `CoupleRepository`/`WorkspaceController` method signatures: `updateUserProfile`/`updatePartnerProfile` (the latter via the `update_partner_profile` RPC), `updateWorkspace`, `updateMetadata` (an upsert, not update), `createWorkspace`/`joinWorkspace`/`recoverWorkspace`/`disconnectWorkspace` (all thin RPC wrappers returning raw maps today — Phase 4's repositories should type these returns too, not just the fetch methods).

**Why first:** every later phase greps for symbols to move or extend. Duplicate `CanvasPoint`, duplicate `_calculateAge`, and misfiled screens make every subsequent search ambiguous. This phase also proves the toolchain (analyze, test, architecture-test) works before any behavioral risk is introduced.

**Files affected:** `lib/repositories/*`, `lib/models/noteit_model.dart`, `lib/models/canvas_document.dart`, `lib/models/timeline_model.dart`, `lib/widgets/theme_selector.dart`, `lib/widgets/timeline_item.dart`, `lib/services/date_helper.dart`, new `lib/core/constants/prefs_keys.dart`, new `test/architecture_test.dart`, new (empty) `lib/features/`.

**Validation:** `flutter analyze` clean; 82 existing tests still pass; add ≥2 new unit tests — closed-form weekend count vs. the old loop's output across a representative multi-year range, and legacy `noteit_model` canvas JSON still round-tripping through `canvas_document`.

## Phase 1 — Extract `CoupleSession` (2–3 days, risk: **high**)

**Scope:** One small `ChangeNotifier` — `CoupleSession` — owning exactly the four fields the fan-out audit identified (`userId`, `coupleId`, `partnerId`, `isSupabaseAvailable`), plus the closely related `isPaired`, `isCreator`, `onboardingCompleted`, and their 5 corresponding `PrefsKeys` entries. It absorbs the auth-listener half of `RelationshipProvider`'s cluster 8 (`relationship_provider.dart:347-611` — the `onAuthStateChange` subscription) and becomes the emitter for `RelationshipLifecycleManager.handlePair`/`handleRepair`/`handleDisconnect`/`handleLogout`.

Add one derived enum, computed once from the five identity fields:
```dart
enum SessionStage { loading, unauthenticated, needsWorkspace, needsCouple, needsGenesis, needsAvatar, ready }
```
This is the readiness contract that go_router's redirect (Phase 3) will consume, replacing today's four independent restatements of "is the user ready."

Rewire all 13 `ChangeNotifierProxyProvider<RelationshipProvider, X>` in `main.dart` to `ChangeNotifierProxyProvider<CoupleSession, X>`. `RelationshipProvider` itself keeps pass-through getters for the four fields so **no UI file needs to change in this phase** — that happens in Phase 5b.

**Why this order:** this is the single change that decouples 13 files from a 2,143-line class, and it must precede Riverpod (Phase 2) — otherwise Riverpod hosts the same fan-out it was meant to fix.

**Files affected:** `lib/main.dart`, `lib/services/relationship_lifecycle_manager.dart`, `lib/providers/relationship_provider.dart` (partial), all 13 domain provider files (one-line signature change each: `updateRelationship(RelationshipProvider)` → `updateSession(CoupleSession)`).

**Risk — high, and deliberately scheduled while the app is still simplest:**
- The auth-listener move could cause `handlePair` to fire before `syncInitialData` completes, or fire twice, producing duplicate realtime subscriptions.
- `SessionStage` computed from partially-hydrated prefs on a cold start could flash `unauthenticated` and incorrectly route a signed-in user to `WelcomeScreen`.

**Validation:** the repository's **first widget tests** — pump `AppHome` against a faked `CoupleSession` for all 7 `SessionStage` values and assert the correct screen renders. This locks the exact contract go_router inherits in Phase 3. Follow with a manual 6-state matrix on a real device with real data: fresh install, creator-unpaired, joiner-unpaired, paired, partner-disconnected, logout.

**Exit criteria:**
- `grep -n "RelationshipProvider" lib/providers/*.dart` returns hits only within `relationship_provider.dart` itself.
- `main.dart` has zero `ChangeNotifierProxyProvider<RelationshipProvider, ...>` entries.
- Exactly one function in the codebase computes "is the user ready for the main app."

**⚠️ Corrected on implementation — three findings, all verified against the actual codebase rather than assumed from this plan's original text:**

1. **12 domain providers, not 13.** `main.dart` has exactly 12 `ChangeNotifierProxyProvider<RelationshipProvider, X>` entries (verified by direct count), matching Phase 6's own "12 domain providers" and `CLAUDE.md`'s provider list. The "13" in this phase's original scope text was an off-by-one; `RelationshipLifecycleManager`'s two base classes (`RelationshipLifecycleProvider`/`SupabaseLifecycleProvider` in `relationship_lifecycle_manager.dart`) are what all 12 actually funnel through, not 13 independent call sites.

2. **`CoupleSession` mirrors `RelationshipProvider`; it does not absorb the auth listener.** This plan's original text said `CoupleSession` "absorbs the auth-listener half of cluster 8... becomes the emitter for handlePair/handleRepair/handleDisconnect/handleLogout." On implementation, `RelationshipProvider`'s `_initSupabaseSync` (`:356-610`) turned out to be one deeply interleaved callback — the user-stream listener sets identity fields (`_coupleId`, `_userId`, `_partnerId`) in the same continuation as profile fields (`_yourName`, `_yourAvatarPath`) and workspace fields (`_startDate`, `_storyTitle`, `_isPremium`), with no seam to split cleanly without either duplicating parts of that callback (risking the exact double-fire/duplicate-subscription failure mode this phase's own risk section warned about) or a much larger rewrite than "2-3 days, high risk" implies.

   The implemented design instead makes `CoupleSession` (`lib/providers/couple_session.dart`) a thin `ChangeNotifier` that mirrors `RelationshipProvider`'s four fan-out fields plus the three pairing/onboarding flags via `updateFromRelationship(RelationshipProvider)`, wired through a `ChangeNotifierProxyProvider<RelationshipProvider, CoupleSession>` in `main.dart` (so the exit criteria above are satisfied in spirit — the 12 domain providers depend on `CoupleSession`, not `RelationshipProvider` — but not in the letter of "zero `ChangeNotifierProxyProvider<RelationshipProvider, ...>` entries," since exactly one remains: the one that builds `CoupleSession` itself). `RelationshipProvider` remains the single source of truth and the sole owner of `handlePair`/`handleRepair`/`handleDisconnect`/`handleLogout` emission until Phase 5 actually decomposes it field by field — at which point `CoupleSession` is "formally ported to a Riverpod Notifier" per this roadmap's own Phase 5, step 1, and becomes the real owner of its own identity fields (and their emission) for the first time. This is lower-risk and reaches the same decoupling outcome (Fact 1) that motivated doing this before Riverpod.

3. **`SessionStage` needs `startDate`, a sixth field, not five.** Wiring `SessionStage` into `main.dart`'s `AppHome` (to satisfy "exactly one function computes readiness," rather than leaving `_buildHomeContent`'s original inline conditional chain in place and merely adding an unused enum) revealed that distinguishing `needsWorkspace`/`needsGenesis`/`needsAvatar` is impossible without `RelationshipProvider.startDate` (verified against `main.dart`'s pre-Phase-1 branches, `:205-214`). `startDate` belongs to `WorkspaceController` (Phase 5), so `computeSessionStage` (a pure function in `couple_session.dart`, deliberately *not* a `CoupleSession` field) takes it as an explicit parameter, and `AppHome` reads it from `RelationshipProvider` directly until Phase 5 lands. `CoupleSession`'s own field set is otherwise exactly as scoped.

**Testing note:** the hydration-style `computeSessionStage` unit tests (`test/couple_session_test.dart`) cover all 7 `SessionStage` values plus two edge branches, and are green. A full widget-pumped `AppHome` test per this phase's original "pump `AppHome` ... for all 7 `SessionStage` values" validation plan was attempted and then removed: it is the first test in this repository to actually render a themed screen, and every themed screen renders text via `GoogleFonts.spectral` — with no font assets bundled for testing, `google_fonts` either attempts a real HTTP fetch (rejected by the test sandbox) or, with `GoogleFonts.config.allowRuntimeFetching = false`, fails its own asset-checksum validation (`_isFileSecure`) rather than falling back silently. This is a pre-existing testability gap unrelated to `CoupleSession`, not something this phase introduced or is positioned to fix; bundling real font files for tests is a separate, future task.

## Phase 2 — Host Riverpod (1 day, risk: low)

**Scope:** Wrap `runApp`'s tree in `ProviderScope`, with the existing `MultiProvider` nested inside it — not replaced. Build the strangler bridge in both directions:

- **Provider → Riverpod:** expose the live `CoupleSession` instance to the Riverpod side via `overrideWithValue` inside a `Consumer<CoupleSession>`, so new Riverpod code reads the *same instance* the old Provider tree uses — one instance, two containers, no state divergence.
- **Riverpod → Provider:** each newly written Riverpod notifier (starting in Phase 5) gets a temporary `ChangeNotifierProvider.value` shim back into `MultiProvider`, so untouched screens can keep calling `context.watch<X>()` unmodified. Each shim is deleted individually once its last `context.watch` call site is converted.

**Why this order:** costs about an hour and means every state unit extracted from Phase 5 onward is *born* as a Riverpod notifier instead of written as a `ChangeNotifier` and migrated a second time later.

**Files affected:** `lib/main.dart`.

**Risk:** low — nothing changes semantically; both trees reference the same underlying objects.

**Validation:** `flutter analyze`; all existing tests pass; one new test asserting override identity (`ref.read(coupleSessionProvider) == context.read<CoupleSession>()` inside a combined widget tree).

**Exit criteria:** `ProviderScope` is the root widget; `coupleSessionProvider` exists and is read successfully by at least one Riverpod-side widget.

## Phase 3 — go_router (4–6 days, risk: medium-high)

**Scope:** Adopt `GoRouter` (ADR-007) with a `redirect` whose body is `switch (session.stage)`, replacing `main.dart`'s `AppHome._buildHomeContent`. Define `lib/routing/routes.dart` as the single named-route registry for the ~20 screen destinations. Convert the 56 `MaterialPageRoute` and 41 `Navigator.push` sites to `context.push(Routes.x)`. Collapse the two conflicting destructive-action strategies (logout's `pushAndRemoveUntil(AppHome)`, deletion's `popUntil(isFirst)`) into one: clear the relevant state, let the redirect recompute the destination. Fix `calendar_screen.dart:581`'s duplicate-shell push (`context.go(Routes.home)` instead). Add a redirect guard on every couple-scoped route returning `Routes.pairing` when `coupleId == null`. Rewrite `notification_service.dart`'s payload handling to resolve a route string and call `_router.go(route)`; delete all 11 of its screen imports and delete `lib/navigator_key.dart`.

**Explicitly left alone:** the 104 `Navigator.pop` sites (`context.pop()` is a drop-in equivalent) and all 32 `showDialog`/14 `showModalBottomSheet` sites (not routes in this app's model — ADR-007).

**Why this order:** *before* the remaining state-ownership work (Phase 5), because `notification_service.dart`'s 11 screen imports mean every screen renamed or split later would otherwise force a fix in the notification service too. Cutting this dependency first means Phase 8's god-screen decomposition doesn't also have to touch notification routing.

**Files affected:** `lib/main.dart`, `lib/navigator_key.dart` (deleted), `lib/services/notification_service.dart`, all 44 files containing imperative navigation, new `lib/routing/`.

**Risk — medium-high:**
- A deep link (notification tap) arriving before `CoupleSession` finishes hydrating must not silently drop the link — `SessionStage.loading` must redirect to nothing (defer), not bounce to `WelcomeScreen`.
- The new route guards are strictly stronger than today's "each screen degrades presentationally" pattern — verify no currently-reachable, legitimate screen state becomes unreachable.

**Validation:** the 7 stage tests from Phase 1 become router redirect tests. One test per notification payload type (12 `feature` values) asserting the correct route resolves. Manual: fire all notification types with the app cold, backgrounded, and foregrounded.

**Exit criteria:**
- `lib/navigator_key.dart` deleted.
- `grep -c "^import.*screens" lib/services/notification_service.dart` == 0.
- `grep -rn "MaterialPageRoute" lib/` == 0.
- Every couple-scoped route has a redirect guard.

**⚠️ Corrected on implementation — five findings, all verified against the actual codebase, plus one deliberate scope narrowing:**

1. **A fresh count found 60 real `Navigator.push`-family sites across 20 files, not "41 across 44."** The `MaterialPageRoute` count (56) held exactly. The literal `Navigator.push` grep undercounted by missing chained/aliased forms (`Navigator.of(context).push(...)`, `state.push(...)` where `state = navigatorKey.currentState`) and included one false positive (a comment). The "44 files" figure was simply wrong — only 20 files under `lib/` contain any of the four navigation patterns.

2. **Redirect reads `RelationshipProvider` directly, not `CoupleSession`.** `CoupleSession.updateFromRelationship` runs on the *next* `ChangeNotifierProxyProvider` rebuild after `RelationshipProvider.notifyListeners()` fires — Provider's proxy mechanism goes through Flutter's `InheritedWidget` dependency system, which defers to the next frame, not synchronously within `notifyListeners()`. A screen doing `await provider.joinWithCode(code); context.push(Routes.avatar);` calls `context.push` — and therefore the redirect — before that next frame; reading `CoupleSession` there would see stale, pre-join values and bounce the push back to `/pairing`. `appRedirect` (`lib/routing/app_router.dart`) reads `RelationshipProvider` directly instead, which has no such lag, and `main.dart`'s `refreshListenable` was simplified to just `relationshipProvider` (dropping the `Listenable.merge` with `CoupleSession`) to match.

3. **The redirect needs an allowed-route-*set* per stage, not a single canonical target.** The original design (`here == target ? null : target`) breaks two real forward-navigation flows: `WelcomeScreen → AuthScreen` (pushed while `stage` is still `unauthenticated`, since sign-in hasn't happened yet) and `PairingSelectionScreen → JoinCoupleCodeScreen`/`RecoverRelationshipScreen` (pushed while `stage` is still `needsCouple`). Without an allowed set, the redirect would immediately bounce these pushes back to `welcome`/`pairing`. `app_router.dart`'s `_allowedRoutesForStage` map fixes this; `computeRedirectTarget` and its tests (`test/app_router_test.dart`) cover both the canonical-target and allowed-set cases for every stage.

4. **The `loading`-defers-a-deep-link mechanism described in this ADR's risk section was not actually implemented until caught by design review.** The first implementation redirected any non-loading location straight to `/loading` and never recorded what the original target was — meaning once `stage` resolved, the "deferred" deep link was simply gone (the user would land on `/home`, not the notification's actual target), contradicting this document's own stated design. Fixed with a small stateful capture/replay in `appRedirect` (`_pendingLocation`, module-level — there is exactly one app-wide router) around the now-pure `computeRedirectTarget`, which re-validates the replayed location against the resolved stage rather than forcing it unconditionally (so a deep link that turns out to be invalid for the resolved stage — e.g. the user was never actually signed in — still lands on the correct onboarding screen, not a couple-scoped route it has no business reaching). Covered by `test/app_router_test.dart`'s "pending deep link replay" group.

5. **Two forward-navigation sites were found to be genuinely unsafe to convert and were deliberately left as plain `Navigator` calls**, each with an inline comment explaining why:
   - `create_couple_code_screen.dart`'s "Continue" button pushes `GenesisScreen` with no gate on `isPaired` — but `computeSessionStage`'s `needsGenesis` requires `isPaired == true` (verified against this app's pre-migration `AppHome` logic, unchanged by this migration). A creator can reach this button before their partner joins, and a router-mediated push would be immediately redirected back to `/workspace`, silently breaking a button that currently works. This is a **pre-existing characteristic of the app's onboarding flow** (present since before this migration), not a regression introduced here — go_router's redirect just makes it manifest immediately instead of only on app restart.
   - `recover_relationship_screen.dart`'s forward push to `AvatarCreationScreen` is gated on `provider.yourName` being empty — a signal `computeSessionStage` doesn't consider at all. A recovered workspace could plausibly still be mid-genesis, in which case the redirect would compute `needsGenesis` and fight the push back to `/genesis`.

   Both are flagged for product/engineering follow-up outside this migration's scope (deciding whether the underlying flows should actually gate on pairing/stage more precisely), not fixed here — this phase changes navigation *plumbing*, not business logic.

6. **Scope narrowing, not a correction:** three widgets — `AddItemDialog`, `EditItemDialog`, `SignatureDrawingDialog` (2 call sites) — are pushed via `Navigator.push`/`MaterialPageRoute` rather than `showDialog`, which puts them outside this ADR's literal "the 41 `Navigator.push` calls that navigate to a distinct screen" wording. They were kept on plain `Navigator` anyway: each is conceptually a dialog (full-screen overlay, typed return value, no deep-link or back-button target of its own), and converting them to named routes would be exactly the over-engineering this ADR's rejected option 2 (route-ifying dialogs) warns against. `test/architecture_test.dart`'s Phase 3 group enforces that `MaterialPageRoute` appears nowhere else.

**Additional findings from the investigation, informing 6a's implementation:**

- **All 12 providers confirmed** against `main.dart`'s provider list, with no naming corrections needed: `TimelineProvider`, `BucketListProvider`, `VaultProvider`, `CalendarProvider`, `NoteitProvider`, `LoveChatProvider`, `TimeCapsuleProvider`, `TopicCardsProvider`, `DailyMoodProvider`, `GiftReminderProvider`, `CurrentlyProvider`, `NotificationPreferencesProvider`.
- **Not a uniform pattern.** 9 of 12 follow the standard `SupabaseLifecycleProvider` single-table-stream shape cleanly. `TopicCardsProvider` and `DailyMoodProvider` bypass the base class's `onRealtimeData()` entirely, each subscribing directly to `RealtimeSubscriptionManager` for **two** tables (`topic_cards`+`topic_card_likes`; `moods`+`daily_questions`, the latter with a non-default composite `primaryKey`) — their Riverpod ports need two `StreamProvider`s each, not one. `NotificationPreferencesProvider` has no realtime subscription at all and is keyed on `userId` alone, not `coupleId` — its port is a plain `AsyncNotifier`/`FutureProvider`, no `StreamProvider`, no `RealtimeSubscriptionManager` involvement.
- **The `love_notes` collision fix is purely client-side** — Supabase Realtime's `.eq()` filters apply server-side at the Postgres replication layer already; the fix is adding a `type` filter param to `SupabaseSyncService.subscribeToCoupleData`/`RealtimeSubscriptionManager.getStream` and folding it into the manager's cache key, no migration needed.
- **Two lifecycle mechanisms currently run in parallel** for all 12 providers: `RelationshipLifecycleManager`'s `handlePair`/`handleRepair`/`handleDisconnect`/`handleLogout` event bus (fired from 4 explicit call sites in `RelationshipProvider`), and `main.dart`'s `ChangeNotifierProxyProvider<CoupleSession, X>.update` chain calling `updateSession()` on every `CoupleSession` rebuild. Both gate on the same `credentialsChanged` check today, so they're redundant rather than conflicting — 6a's Riverpod ports keep only the `updateSession`-equivalent spirit, via a push from a bridge widget (see unit 1's findings below), matching ADR-005.
- **`CurrentlyProvider.syncInitialData()` never sets `_state`** — only `_loadHistory()` runs, so `LoveTapState` stays `idle` until the first realtime event arrives. Pre-existing behavior, not introduced by this migration; preserved as-is in the port rather than silently "fixed," since correcting it wasn't asked for.
- **`MusicProvider` is dead, unregistered code** (not part of the 12) — never added to `buildAppProviders()`, and its sole consumer `music_controls.dart` is never imported anywhere. Flagged for a future cleanup pass, out of scope for this phase.

**Unit 1 (`BucketListController`) — the proof of the Riverpod port pattern the other 11 providers follow:**

1. **A shared `SupabaseLifecycleNotifier<T>` mixin (`lib/core/riverpod/supabase_lifecycle_notifier.dart`) replaces the old `RelationshipLifecycleProvider`/`SupabaseLifecycleProvider` base classes.** It provides `initSessionLifecycle()` (called once from each concrete `build()`), `initRealtime()`/`disposeRealtime()` (wrapping `RealtimeSubscriptionManager.getStream(...)`, same as before), and `updateSession(CoupleSession)` (the same `credentialsChanged`-gated sync/purge/subscribe logic as the old base class). Concrete notifiers `with` this mixin and implement `tableName`, `syncInitialData()`, `purgeCache()`, `onRealtimeData()` — the same three hooks the old `SupabaseLifecycleProvider` subclasses implemented, just Riverpod-shaped. This mirrors the old base-class role closely enough that 9 of the remaining 11 providers (the ones following the standard single-table pattern per the investigation above) should port with comparatively little new design work; `TopicCardsProvider`/`DailyMoodProvider` (dual-table) and `NotificationPreferencesProvider` (no realtime) will each need a variant.

2. **Session-change propagation is a single new bridge widget, `main.dart`'s `_DomainProvidersBridge`, not per-provider Riverpod reactivity.** `coupleSessionProvider` is a one-shot bridge onto the live `CoupleSession` instance (Phase 2's strangler bridge), not itself Riverpod-reactive, so a domain notifier's `build()` can't just `ref.watch` it to pick up future changes. `_DomainProvidersBridge` watches `CoupleSession` via `context.watch<CoupleSession>()` (the same Provider-package type the old 12 providers watched) and pushes every change into each ported notifier via `ref.read(xControllerProvider.notifier).updateSession(session)` — the Riverpod-native equivalent of `main.dart`'s old `ChangeNotifierProxyProvider<CoupleSession, X>.update` chain. One bridge for all 12, not one per provider like the Phase 5 mirror bridges, since every domain provider reacts to the identical trigger with no per-provider divergence in *when* to update.

3. **A real `autoDispose` race was found and fixed, not just a testing inconvenience.** `bucketListControllerProvider` is `NotifierProvider.autoDispose` (per the roadmap's own instruction). The very first test written against it failed: `container.read()` doesn't establish a Riverpod listener, so the provider was torn down before `build()`'s fire-and-forget `_loadFromCache()` (an async SharedPreferences read) resolved, and the subsequent `state =` write threw `Cannot use the Ref ... after it has been disposed` — silently swallowed as an uncaught Future error rather than crashing, but the load's result was discarded either way. This is not test-only: in production, if a domain screen is closed (last watcher removed) while an async `syncInitialData`/write method is still in flight, the same disposal can race the same way. Fixed by adding `if (!ref.mounted) return;` immediately after every `await` that precedes further `state`/`ref` access, in both `BucketListController` itself and the shared mixin's `updateSession`. This guard is now the established convention for every remaining provider's port, not optional per-provider judgment. Tests hold the provider alive correctly via `container.listen(provider, (_, __) {})` before exercising async methods — a bare `container.read()` is not sufficient for an `autoDispose` provider under test, matching Riverpod's own documented testing guidance.

4. **A genuine, pre-existing production bug was found and *not* fixed:** `BucketListItem.copyWith`'s `completedAt: completedAt ?? this.completedAt` means passing `completedAt: null` (as `toggleItem` does when un-completing an item) never actually clears the field, since `null ?? this.completedAt` falls back to the old value — un-completing a bucket list item silently leaves its stale `completedAt` timestamp in place. This bug is in the original `BucketListProvider.toggleItem` too (identical call, identical model), so it already exists in production today, independent of this migration. Preserved as-is in the port; the test written against it was written to assert the actual (buggy) behavior with an inline explanation, not silently "fixed" as a drive-by — Phase 6a's job is a faithful behavior port, not a bug hunt. Worth a follow-up bug-fix task outside this migration's scope.

5. **`lib/features/bucket_list/` is the first of the 12 target feature directories** (`bucket_list_state.dart` + `bucket_list_controller.dart`), matching `feature-boundaries.md`'s naming (`bucket_list`, not `bucketList` or `bucket_list_provider`). The existing `BucketListItem` model (`lib/models/bucket_list_model.dart`) was reused unchanged — already immutable with `copyWith` from Phase 4, no reason to duplicate it under `features/`.

**Units 2-4 (`GiftReminderController`, `CalendarController`, `TimeCapsuleController`) — same pattern, one real behavioral gotcha caught by review, not by a failing test:**

6. **All three follow unit 1's established `SupabaseLifecycleNotifier` + `ref.mounted`-guard pattern directly** — `lib/features/gift_reminders/`, `lib/features/calendar/`, `lib/features/love_studio/` (the last matching `feature-boundaries.md`'s naming for the `time_capsules` table, not `time_capsule`). Each shipped with its own test file (6-7 tests) and wired into `main.dart`'s single `_DomainProvidersBridge`.

7. **A real port-fidelity bug was caught during self-review, before it reached a test run:** unlike `BucketListProvider`, none of `GiftReminderProvider`/`CalendarProvider`/`TimeCapsuleProvider`'s write methods apply their change locally on the Supabase success path — all three rely entirely on the realtime echo to update state after a successful write, only applying locally on failure or while unpaired. The first draft of `GiftReminderController.updateReminder`/`deleteReminder` incorrectly added an unconditional local apply after the try/catch (extrapolating unit 1's `BucketListProvider` pattern instead of checking this provider's actual original behavior), which would have made reminders appear to update/delete instantly even when still paired — a real, if subtle, behavioral drift from production. Caught by re-reading the original source line-by-line before moving on, not by a test (no test happened to cover the paired-success path, since these tests all run unpaired). Fixed before `CalendarController`/`TimeCapsuleController` were written, and the "does this provider apply locally on success, or wait for the realtime echo?" check was applied explicitly to each from then on — it varies per provider and cannot be assumed from a sibling's behavior.

**Unit 5 (`TimelineController`) — the widest UI consumer surface (18 files) and the largest single provider (796 lines original), ported without a UI conversion since the mirror-vs-cutover lesson from Phase 5 still applies: `lib/screens/love_story_screen.dart` and 17 others keep reading `TimelineProvider` directly, unaffected by this unit:**

8. **`deleteTimelineItem` is deliberately, and correctly, asymmetric with `addTimelineItem`/`updateTimelineItem`.** Add/update never apply locally on the Supabase success path (same as units 2-4). Delete is the opposite: it always applies immediately and optimistically, paired or not, guarded by `_locallyDeletedIds` so the realtime stream can't resurrect a just-deleted item mid-flight before the DB delete lands. Both behaviors were verified against the original line-by-line before porting, given the item-7 lesson that this asymmetry can't be assumed.

9. **`LocalPersistenceService` (not raw `SharedPreferences` JSON like the other four controllers) is the local cache**, reused unchanged — it's already couple-agnostic and has no Supabase dependency (see its own doc comment, a Phase 0 rename from `TimelineRepository`). `pickImage(BuildContext)` — the one method needing a `BuildContext` (for `PermissionService`'s photo-permission prompt) — ported as-is; a `Notifier` method can take a `BuildContext` argument from its caller exactly as a `ChangeNotifier` method could, no different handling needed. Not covered by `timeline_controller_test.dart` since it needs real `image_picker`/permission platform channels, consistent with this repo's existing convention of not unit-testing platform-heavy methods.

10. **One accepted, structural deviation, flagged rather than fought:** the original `reorderTimelineItems`, on its Supabase-paired success path, mutates `_timelineItems` in place and never calls `notifyListeners()` at all — the UI only catches up once the realtime echo for the same reorder arrives and `onRealtimeData` notifies for real. This is a latent lag bug in production today (reordering while paired doesn't visibly move the item until a round-trip completes), not something introduced by this port. It could not be faithfully reproduced in Riverpod even if desired: a `Notifier`'s `state =` is the only way to change state and it always notifies watchers immediately — there is no equivalent of mutating a private field without notifying. `TimelineController`'s port therefore shows the reorder immediately on the paired-success path, a strict improvement over the original's behavior, accepted as an unavoidable consequence of the state model rather than something requiring a workaround.

**Unit 6 (`VaultController`) — the one provider mixing in `WidgetsBindingObserver` for auto-lock on app pause:**

(A first attempt used `implements WidgetsBindingObserver` and hand-stubbed every interface member; abandoned once several stub signatures didn't type-check against this Flutter SDK version's exact interface shape — `with` is both correct and far less code.) `test/vault_controller_test.dart` needed `TestWidgetsFlutterBinding.ensureInitialized()` as its first line, the one test file among the six domain-provider ports so far that requires it, since `WidgetsBinding.instance` throws until a binding exists.

Confirmed via a full grep of every `.photos`/`.letters` call site before concluding it's safe today. Not hardened here — Phase 6a's job is a faithful port; changing the model's self-gating contract without touching the one call site it protects could create a footgun for whoever eventually converts that screen without noticing the getters aren't self-gated. `VaultState`'s duplicate `items`/`allItems` getters (identical in the original) were collapsed into one `visibleItems` getter, since nothing depends on the exact getter name yet (no UI conversion has happened) and the original duplication served no purpose.

13. **`setPin`/`verifyPin`'s `FlutterSecureStorage` calls have no platform channel in a plain unit test**, so they throw and the code falls through to its own pre-existing `'vault_pin_fallback'` SharedPreferences fallback on both the write and read sides — meaning `test/vault_controller_test.dart`'s PIN tests exercise a real production code path (the fallback for when secure storage is unavailable on-device), not a test-only shortcut.

**Units 7-8 (`NoteitController`, `LoveChatController`) — ported together since both read the shared `love_notes` table, and the unit that surfaced this phase's most consequential finding:**

14. **The planned `love_notes` "collision fix" (distinct subscription keys, server-side `type` filtering) turned out to be technically infeasible, not just deprioritized — and the "collision" was never actually a bug.** Verified directly against the installed `supabase` package (2.13.0) source: `.stream()`'s filter builder stores exactly one `.eq()` filter, and a second call overwrites rather than combines it — `.eq('couple_id', ...).eq('type', ...)` would silently drop the couple scoping, a far worse bug than the one it was meant to fix. `NoteitController`/`LoveChatController` both keep `tableName => 'love_notes'`, sharing the mixin's default subscription key exactly as the original providers did, each still filtering client-side in `onRealtimeData` — this is `RealtimeSubscriptionManager`'s deduplication doing its job, not debt. **ADR-005 and ADR-013 have been corrected in place** (their own "Corrected on implementation" sections) to retract the server-side-filter plan and the "confirmed bug" framing.

15. **`NoteitSyncManager`'s singleton ownership was deliberately NOT transferred to `NoteitController` this unit** — see `noteit_controller.dart`'s doc comment for the full reasoning. The manager holds one `NoteitProvider? _provider` reference, set via `initialize()`, currently called only from the old `NoteitProvider.updateSession`. Since the old provider is still what `noteit_screen.dart` reads (Phase 6a doesn't convert UI), having `NoteitController` also call `initialize()` from its own `updateSession` would race the two for the singleton's one slot on every pairing event — and since nothing reads `NoteitController` yet, "winning" that race would only cost the *old*, actually-in-use provider its sync status updates, a real regression for zero benefit today. `NoteitController`'s send methods still call `NoteitSyncManager.instance.enqueue(...)` (the actual Supabase writes succeed regardless of which provider "owns" the manager), but its own `updateItemSyncStatus` won't be reached by the queue's callbacks until Phase 6b retires the old provider and this controller becomes the sole `initialize()` caller. Flagged as a real, if currently dormant, limitation — nothing exercises this path today.

16. **`ref.keepAlive()` (ADR-005's `keepAlive` requirement for chat and scrapbook) is applied to both controllers' `build()`**, exempting them from `autoDispose`'s default teardown so a brief background/tab-switch can't drop an in-flight realtime subscription and the messages that would have arrived during the gap.

17. **A major, retroactive correctness finding: every Phase 6a domain controller (and Phase 5's `LicenseController`) needed `dependencies: [coupleSessionProvider]` added to its provider declaration, and didn't have it until this unit.** `main.dart`'s strangler bridge overrides `coupleSessionProvider` only in a *nested* `ProviderScope` (`Consumer<CoupleSession>`'s child), not the outer root one — because `CoupleSession` doesn't exist until the Provider tree builds. Riverpod homes any provider with no explicit `dependencies:` declaration in the *root* container the first time anything reads it, regardless of which nested scope's `ref` triggered that read — so every domain controller's own internal `ref.read(coupleSessionProvider)` (via `SupabaseLifecycleNotifier`) was resolving against the un-overridden root and throwing `UnimplementedError`, unconditionally, the first time any of them was actually read through the real widget tree. This was **invisible in every controller test written so far**, because each uses a bare `ProviderContainer(overrides: [coupleSessionProvider.overrideWithValue(...)])` with no root/nested distinction to get wrong. It surfaced only because `_DomainProvidersBridge` (introduced in unit 1) is the first bridge to eagerly `ref.read(x.notifier)` several dependent providers unconditionally on every frame, and `test/riverpod_bridge_test.dart` — a pre-existing Phase 2 test, the only one in the suite that pumps `buildAppRoot()` (the real, full two-`ProviderScope` production tree) rather than a flat container — started failing as a direct result. Fixed by adding `dependencies: [coupleSessionProvider]` to all 8 Phase 6a controllers' provider declarations plus `licenseControllerProvider` (retroactive Phase 5 fix); `profileControllerProvider`/`workspaceControllerProvider`/`presenceControllerProvider` don't need it, since they never read `coupleSessionProvider`. **Full correction detail, including why this session's actual bridge-push design sidesteps a second, independent flaw in the originally-planned `ref.watch(coupleSessionProvider)` reactivity pattern, is in `docs/architecture/state-management.md`'s own "Corrected on implementation" section** — read that before adding the 9th domain provider or any future provider that touches `coupleSessionProvider`, since the omission has no compile-time or analyzer signal, only a runtime one, and only when exercised through the real production tree.

18. **Testing-strategy implication, noted but not acted on this unit:** `test/riverpod_bridge_test.dart` being the *only* test that pumps the real production tree, rather than a flat `ProviderContainer`, means bugs of exactly this shape (root-vs-nested-scope resolution) will keep going undetected by every other controller test in the suite. Worth a deliberate decision in a future unit about whether more of the domain-controller test suite should pump `buildAppRoot()` instead of (or in addition to) a bare container — flagged here rather than expanded unilaterally, since it's a testing-strategy scope change, not a mechanical fix.

**Units 9-10 (`TopicCardsController`, `DailyMoodController`) — the two providers investigation flagged as needing a dual-table variant, confirming that assumption exactly:**

19. **Both override `initRealtime()`/`disposeRealtime()` directly rather than using `SupabaseLifecycleNotifier`'s single-table default**, matching the originals' own shape: `TopicCardsController` runs two independent `RealtimeSubscriptionManager` subscriptions (`topic_cards`, `topic_card_likes`); `DailyMoodController` runs two more (`moods`, `daily_questions` — the latter with a non-default composite `primaryKey: ['date', 'couple_id']`). `onRealtimeData()` is a no-op on both, matching the originals' own "handled by overriding initRealtime due to multiple tables" comment. The shared mixin's `initSessionLifecycle()`/`updateSession()`/`coupleId`/`sessionUserId` are still used for everything except the realtime wiring itself — the dual-table shape only required overriding two methods, not abandoning the mixin.

20. **`DailyMoodController.updateSession` also overrides, mirroring the original's `DailyMoodProvider.updateSession`**, to capture `CoupleSession.partnerId` into a private field before calling `super.updateSession(session)` — needed for `answerDailyQuestion`'s and the realtime question handler's partner-answer lookup, which key into the `daily_questions` row's `answers` map by partner user ID. Kept as controller-only bookkeeping (not part of `DailyMoodState`), consistent with every other controller's `_localMutations` convention.

This port's `activeDeck` is a pure derived getter over `customCards`/`likedCardIds`/`activeCategory`, none of which shuffling would change, so there is no state to mutate that would actually reorder anything. Left as a documented no-op with an inline comment rather than either faking a shuffle that doesn't affect derived state or introducing a new stored-order field the original didn't have; flagged here for whoever converts the topic-cards screen in Phase 6b to decide whether `activeDeck` needs to become stored state at that point.

22. **Both `dependencies: [coupleSessionProvider]` were added from the start** (unlike units 1-8, which needed the retroactive fix in unit 8's finding above) — this pair was written after that fix was already understood, so both provider declarations shipped correct the first time.

**Units 11-12 (`CurrentlyController`, `NotificationPreferencesController`) — the last two of the 12, closing out the domain-provider port:**

23. **`CurrentlyController` is a standard single-table port** with one overridden method (`updateSession`, mirroring the original, to capture `partnerId` for the deterministic partner1/partner2 tap ordering) — no new findings beyond what units 1-10 already established. `syncInitialData`'s pre-existing quirk (never sets `state`, only refreshes `history` — confirmed during the original Phase 6 investigation) is preserved exactly, per the same "preserve, don't fix" rule applied throughout this phase.

Instead it reproduces `RelationshipLifecycleProvider`'s smaller (non-Supabase) `updateSession` contract directly: track `_userId`/`_coupleId`, call `syncInitialData()`/`purgeCache()` on a credentials change. **A non-obvious gating behavior was found and preserved rather than fixed:** the inherited base class only ever calls `syncInitialData()` when *both* `coupleId` and `userId` are non-null, even though this provider's own logic only reads `userId` — meaning a signed-in-but-unpaired user's notification preferences never load until pairing completes. Identity comparison can't observe the dedup this suite exists to verify, so a minimal, testing-only accessor into the manager's existing internal key-presence map was the correct fix — not a redesign, not a workaround, just a way to ask the question the tests actually need answered.

## Phase 6b — Make `CoupleSession` real; finish removing `RelationshipProvider`

**⚠️ Corrected on implementation — a repo-wide investigation before writing any code found the phase is substantially larger than its framing implied, on three independent axes. None of this was known when Phase 6b was named in Phase 6a's own corrections above.**

**1. The realtime split needs a hub, not independent per-controller subscriptions — confirmed technically infeasible another way, not just riskier.** `RelationshipProvider._initSupabaseSync()` (`:286-540`) opens direct `users`/`couples` streams that bypass `RealtimeSubscriptionManager` entirely (`SupabaseSyncService.subscribeToCoupleData` hardcodes `.eq('couple_id', ...)`, which `couples` doesn't even have as a column — a literal per-controller `RealtimeSubscriptionManager.getStream(tableName: 'couples', ...)` call would error, not just risk a duplicate subscription). Worse: the auth callback calls `Supabase.instance.client.removeAllChannels()` unconditionally on **every** `onAuthStateChange` event (`:293`) — including routine `tokenRefreshed` events that fire roughly hourly during any live session, not just sign-in/out — a global teardown of every feature's realtime channels, not just `RelationshipProvider`'s own. Four or five independent controllers each running their own auth listener and each calling this would race destructively. And `CoupleSession`'s own `partnerId`/`isPaired` are derived *inside* the `couples`-stream callback, which `ProfileController`'s and `PresenceController`'s partner-scoped realtime work depend on being resolved first (`_initPartnerUserSync`/`_initPresence` are literally called from inside that same callback, `:490-494`) — a real data-sequencing dependency, not just an organizational one. **Conclusion: `CoupleSession` must be the sole owner of the auth listener and the raw `users`/`couples` subscriptions, re-emitting derived state the other controllers read** — a hub, not four independent listeners.

**2. Nearly all 27 UI files need write-method conversion, not just read conversion — and none of Phase 5's three mirror controllers have any write methods at all.** Confirmed by direct inspection: `ProfileController`/`WorkspaceController`/`PresenceController` each expose exactly `build()` and `updateFromRelationship(RelationshipProvider)` — nothing else. Every one of `setYourName`/`setAvatars`/`setNames`/`setStoryTitle`/`setStartDate`/`setStartTime`/`setPremium`/`generateCoupleCode`/`refreshPairingCode`/`regenerateRecoveryCode`/`clearRecoveryCode`/`updateCurrentActivity`/`joinWithCode`/`createRelationshipWorkspace`/`recoverRelationship`/`unlinkPartner`/`completeOnboarding`/`deleteAccount`/`logout`/`signUpWithEmail`/`signInWithEmail`/`signInWithGoogle`/`clearPartnerDeletedNotice` exists **only** on `RelationshipProvider` today, and nearly every one of the 27 files calls at least one of them. "Convert the UI files to read the Riverpod controllers instead" (this phase's original framing) describes only the read half — the actual job is a full cutover of the remaining ~850-line write-method surface (`relationship_provider.dart:664-1369`), given real Riverpod homes across CoupleSession/Profile/Workspace/Presence, before or alongside the UI conversion.

**3. This phase's own exit criteria (`provider:` removed from `pubspec.yaml`, `MultiProvider` gone from `main.dart`) are unreachable within the scope named so far.** Two more `ChangeNotifier`s live in the same `MultiProvider` tree and were never mentioned in any phase of this roadmap: `ThemeProvider` (39 files read it) and `RecentActivityProvider` (1 file). Neither has any Riverpod counterpart. Separately, `go_router`'s `refreshListenable` (`main.dart:402-403`) is wired directly to the live `RelationshipProvider` instance as a `Listenable`, and `appRedirect` (`app_router.dart:141`) reads it synchronously inside the redirect callback with an explicit comment explaining why it can't read `CoupleSession` today (the one-frame mirror lag — which disappears once `CoupleSession` is real, but the redirect's read mechanism and the `refreshListenable` wiring still need a concrete replacement, e.g. a `GoRouterRefreshStream`-style adapter over the new `CoupleSession` Notifier). Deleting `RelationshipProvider` and removing `provider:` cannot both happen without resolving this wiring and porting (or explicitly descoping) `ThemeProvider`/`RecentActivityProvider`.

**Smaller findings, informing implementation once scope is settled:**

**⚠️ Corrected immediately on further design work, before any 6b-1 code was written: 6b-1 as scoped ("no UI touched yet") is not achievable, for a reason that is the exact same lesson Phase 5's own correction #1 already established once.** `RelationshipProvider`'s auth listener (`_initSupabaseSync`) cannot keep running once `CoupleSession` owns its own independent copy — §5's finding that the callback's unconditional `removeAllChannels()` (firing on every `onAuthStateChange` event, including routine hourly `tokenRefreshed` events) makes two *independent* listeners destructively race applies just as much to "`CoupleSession`'s new listener" vs. "`RelationshipProvider`'s old listener" as it did to "four independent domain controllers." **Unit 1 (`CoupleSession`) — implemented, and the "reverse mirror needs a global `ProviderContainer`" premise above turned out to be wrong for the read half, which changed the actual shape of this unit:**

1. **The read-side shim is not a Riverpod problem at all, because `CoupleSession` never had to become a Riverpod `Notifier`.** The correction above conflated two different things: `RelationshipProvider`'s *write* methods needing to call into Riverpod state (genuinely hard without a `WidgetRef`/`ProviderContainer`) and `RelationshipProvider` needing to *observe* `CoupleSession`'s changes (not hard at all). `CoupleSession` was staying a plain `ChangeNotifier` regardless — it already occupied that exact slot in `main.dart`'s `MultiProvider` tree since Phase 1, feeding the 12 domain providers via `ChangeNotifierProxyProvider<CoupleSession, X>`, which only works because `CoupleSession` is a `Listenable`. Since it stayed one, `RelationshipProvider` can hold a plain reference to the live instance and call `session.addListener(_onSessionChanged)` in its own constructor — an ordinary Dart object relationship, not Riverpod, not a global container, not a widget-tree bridge. 2. **This makes the "convert CoupleSession's own UI consumers now" half of the plan moot, in a good way: zero UI files needed to change.** `RelationshipProvider` becomes a pass-through facade — every one of its ~35 getters and write methods now delegates one line to `_session`, preserving the exact public API the ~24 UI files (`context.watch`/`read<RelationshipProvider>()`) already call. ## Phase 6b-3 — Finish the stranded duration/milestone-math extraction

**Scope:** exactly what ADR-009 originally called for during Phase 5 and never happened: move `startDateTime`, `relationshipDuration`, `totalDays`, `totalHours`/`totalMinutes`/`totalSeconds`, `preciseAge`, `totalMonths`, `relationshipAge`, `years`, `nextMilestones`, `MilestoneInfo`, and the private `_getOrdinal` helper off `RelationshipProvider` and into plain, parameterized `DateHelper` functions — `DateHelper.relationshipStartDateTime(startDate, startTime)`, `relationshipTotalDays(startDate)`, `relationshipPreciseAge(startDate, startTime)`, `relationshipTotalMonths(startDate)`, `relationshipAgeLabel(startDate, startTime)`, `nextRelationshipMilestones(startDate, startTime)` — with `MilestoneInfo` itself moving to `date_helper.dart`.

**Implementation:**

1. **`RelationshipProvider`'s own getters were kept, converted to one-line delegations to the new `DateHelper` functions,** rather than deleted outright — the 9 files this phase unblocks still need converting (that's the next step, not this one), and per this migration's established practice, delegation is preferred over duplication wherever a real implementation already needs to exist somewhere. `relationship_provider.dart` re-exports `MilestoneInfo` from `date_helper.dart` (`export 'package:days_together/services/date_helper.dart' show MilestoneInfo;`) so files still importing it from the old location don't break before their own conversion turn comes.

2. **Every new function takes `DateTime? startDate` (and `TimeOfDay? startTime` where the original used it) as plain parameters** rather than reading any provider's private state — this is what actually unblocks the 9 stranded files: any of them can now call `DateHelper.relationshipTotalDays(workspace.startDate)` using `WorkspaceController`'s already-real `startDate` field, with no `RelationshipProvider` dependency at all.

3. **Validation:** new `DateHelper relationship duration/milestone math` test group in `test/date_helper_test.dart` (9 tests) covering null-startDate defaults, `relationshipStartDateTime`'s date/time combination and "now" fallback, and cross-checking `relationshipTotalDays`/`relationshipPreciseAge`/`nextRelationshipMilestones` against their constituent primitives. A new test in `test/relationship_provider_test.dart` confirms the facade's getters still produce values identical to calling the `DateHelper` functions directly with `CoupleSession`'s own `startDate`/`startTime` — proving the delegation wiring, not just the underlying math, is correct. One test-writing mistake caught immediately: `relationshipAgeLabel`'s days component pluralizes only above 1 day (a faithful match of the original getter's `> 1` check, not `!= 1`), so a same-day start renders "0 Day" singular, not "0 Days" — the test's own first draft got this wrong, not the extracted code. `flutter analyze` clean; full suite green at 274 tests (up from 265), with one confirmed pre-existing failure unrelated to this phase — `typography_test.dart`'s Google Fonts test-environment gap, already documented in Phase 1's corrections.
